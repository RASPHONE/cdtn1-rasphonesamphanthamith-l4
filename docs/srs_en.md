## 1. Introduction and Scope

### 1.1 Context

Mekong Mobile operates 6 warranty service centers. Warranty tickets are currently received on paper, and center managers assign technicians manually by memory. This causes two problems from the case study:

- **V2:** paper warranty tickets are hard to track, leading to overdue tickets;
- **V3:** manual technician assignment causes workload imbalance and skill mismatch.

This SRS specifies flow **L4 — Technician Assignment and Appointment Scheduling**. L4 consumes warranty tickets already created by flow L2 and allows the center manager to assign a qualified technician and schedule a handover/receipt appointment.

### 1.2 Scope in one sentence

Manage technician assignment and appointment scheduling for warranty tickets: the center manager reviews incoming warranty tickets, the system identifies technicians qualified for the ticket's issue category and working at the same service center, the manager assigns at most one technician while considering current workload, then creates or confirms the customer's device handover/receipt appointment, checks for appointment conflicts, and finishes when the assignment is saved and the appointment is confirmed.

### 1.3 Out of scope and intentionally deferred

The following capabilities are explicitly excluded from v0.2:

1. **Customer-facing portal.** Customers do not log in, confirm, reschedule, or receive system notifications. The center manager acts on the customer's behalf.
2. **Notification infrastructure.** No SMS, email, or push notification is sent by the system in v0.2.
3. **Technician self-service UI.** The Technician actor is specified but deferred to v1.1.
4. **Reporting and analytics.** Dashboards belong to flows L6/L10, not L4.
5. **Authentication provider.** Login is treated as infrastructure, not a business flow.
6. **On-site check appointment workflow.** The appointment type `KIEM_TRA_TAI_CHO` is retained in the database enum for historical/generated data compatibility, but v0.2 only allows creating `GIAO_MAY` and `NHAN_MAY` appointments.
7. **Structured appointment location and appointment note.** No `location` or `note` field is stored for appointments in v0.2. Handover/receipt appointments are associated with the ticket's service center. On-site address handling and appointment notes are deferred.

### 1.5 Data source and working subset

L4 depends on tickets created by L2. For the prototype, L4 works with a filtered subset of the case study dataset:

- base dataset seed: `20260901`;
- appointment fixtures generated separately;
- recommended appointment generation command:

```bash
python tools/gen_sample.py --entity appointment --rows 1200 --seed 42 \
  --link tickets_history.csv --out appointments.csv
```

The estimated **~40,200 records** refer to a filtered L4 working subset, not the full 187,650-row case study dataset. The subset includes warranty tickets relevant to assignment, their related status-log records, generated appointment records, and the master data needed for technician qualification and scheduling.

### 3.2 User Stories implemented or supported in BT2

**US1 (MUST).** As a center manager, I want to see all unassigned warranty tickets for my service center sorted by due date, so that I can start assigning before tickets are forgotten.

**US2 (MUST).** As a center manager, I want the system to suggest technicians who have proficiency ≥ 3 in the warranty ticket's issue category and work at the same service center, so that I do not assign a repair to a technician without the required skill.

**US3 (SHOULD).** As a center manager, I want to see each qualified technician's current open warranty ticket count, so that I can balance workload instead of assigning by memory.

**US4 (MUST).** As a center manager, I want to assign or reassign a warranty ticket to exactly one qualified technician, recording a reason when the technician is changed, so that ownership is clear and traceable.

**US5 (MUST).** As a center manager, I want to schedule and confirm a device handover or receipt appointment for an assigned warranty ticket, choosing either `GIAO_MAY` or `NHAN_MAY`, so that the appointment is recorded and the technician's schedule is updated.

**US6 (MUST).** As a center manager, I want the system to warn and block me when an appointment conflicts with the technician's existing active appointments, so that I avoid double-booking.

**US8 (SHOULD).** As a center manager, I want to filter unassigned warranty tickets by issue category and priority, so that I can batch assignments by skill area.

**US12 (SHOULD).** As a center manager, I want to maintain technician skill records for technicians in my center so that qualified-technician suggestions reflect current proficiency.

**US13 (SHOULD).** As a center manager, I want to soft-delete erroneous active appointments so that they no longer affect scheduling while the record remains for traceability.

### 3.4 Acceptance Criteria for MUST Stories

#### US1

- **AC1.** GIVEN a center manager is logged in and belongs to service center X, WHEN they open the unassigned warranty ticket list, THEN the system shows only tickets with `status = MOI`, `is_warranty = true`, `center_id = X`, `technician_id IS NULL`, and `is_deleted = false`, sorted ascending by `due_date`.
- **AC2.** GIVEN there are no unassigned warranty tickets for service center X, WHEN the manager opens the list, THEN the system shows an empty-state message and hides the Assign action.
- **AC3.** GIVEN a center manager belongs to service center X, WHEN they try to view unassigned tickets of service center Y, THEN the system denies access and returns HTTP 403.

#### US2

- **AC1.** GIVEN a warranty ticket has issue category `MAN_HINH` and belongs to service center 2, WHEN the manager opens the assignment screen, THEN the system lists technicians where `center_id = 2`, `is_active = true`, and proficiency for `MAN_HINH` ≥ 3.
- **AC2.** GIVEN no technician at service center 2 has proficiency ≥ 3 for the ticket's issue category, WHEN the manager opens the assignment screen, THEN the system shows "No qualified technician available" and disables the Assign action.
- **AC3.** GIVEN a technician has proficiency = 2 for the ticket's issue category, WHEN the system suggests technicians, THEN that technician is not included in the qualified list.

#### US4

- **AC1.** GIVEN an unassigned warranty ticket in `MOI` status and a qualified technician selected, WHEN the manager confirms assignment, THEN the system saves `technician_id`, changes ticket status to `DA_PHAN_CONG`, and writes a `ticket_status_log` entry.
- **AC2.** GIVEN the warranty ticket is already assigned to technician A, WHEN the manager changes it to technician B without entering a reason, THEN the system rejects the change and displays "Reason is required when changing technician."
- **AC3.** GIVEN the selected technician does not have proficiency ≥ 3 for the ticket's issue category or belongs to a different service center, WHEN the manager confirms assignment or reassignment, THEN the system rejects with a validation error.

#### US5

- **AC1.** GIVEN an assigned warranty ticket, WHEN the manager enters a valid `ngay_hen`, `gio_bat_dau`, `gio_ket_thuc`, and `loai = GIAO_MAY` or `NHAN_MAY`, and confirms, THEN the system creates the appointment linked to the ticket, the assigned technician, and the ticket's service center with `trang_thai = DA_XAC_NHAN`.
- **AC2.** GIVEN the combination of `ngay_hen` and `gio_bat_dau` is earlier than the current date and time, WHEN the manager saves, THEN the system rejects the appointment and displays "Appointment time must be in the future."
- **AC3.** GIVEN one of the required appointment fields (`ngay_hen`, `gio_bat_dau`, `gio_ket_thuc`, `loai`) is missing, WHEN the manager saves, THEN the system rejects the save, highlights missing fields, and keeps entered data.
- **AC4.** GIVEN `gio_ket_thuc` is not after `gio_bat_dau`, WHEN the manager saves, THEN the system rejects the save and displays "End time must be after start time."

#### US6

- **AC1.** GIVEN technician T has an existing appointment on the same `ngay_hen` from 09:00–10:00 with `trang_thai = DA_DAT` or `DA_XAC_NHAN`, WHEN the manager creates an appointment 09:30–10:30 for T, THEN the system warns of conflict and blocks saving until the time is changed or the manager cancels.
- **AC2.** GIVEN the overlapping appointment belongs to a different technician, WHEN the manager saves, THEN the system saves without a conflict warning.
- **AC3.** GIVEN the manager updates an existing appointment to a time that overlaps another active appointment of the same technician on the same `ngay_hen`, WHEN the manager saves, THEN the system warns and blocks the update.
- **AC4.** GIVEN the overlapping appointment has `trang_thai = HOAN_TAT`, `KHACH_HUY`, or `KHACH_KHONG_DEN`, WHEN the manager saves, THEN the system saves without a conflict warning.

### 3.5 Acceptance Criteria for BT2 CRUD Support Stories

#### US12 — Technician skill maintenance

- **AC1.** GIVEN an active technician and an active issue category, WHEN the manager creates a skill with proficiency 4, THEN the system saves the skill and it appears in the technician skill list.
- **AC2.** GIVEN the technician already has a skill for the same category, WHEN the manager creates the same skill again, THEN the system rejects the request with HTTP 409.
- **AC3.** GIVEN proficiency is 0 or 6, WHEN the manager creates or updates a skill, THEN the system rejects the request with HTTP 422.
- **AC4.** GIVEN an existing skill, WHEN the manager deletes it, THEN the skill row is removed and the technician is no longer qualified through that skill.

#### US13 — Appointment soft delete

- **AC1.** GIVEN an active appointment, WHEN the manager requests DELETE, THEN the system sets `appointment.is_deleted = true` and returns success.
- **AC2.** GIVEN a soft-deleted appointment, WHEN the manager reads the default appointment list, THEN the appointment is not shown.
- **AC3.** GIVEN a soft-deleted appointment, WHEN the manager creates another appointment at the same time for the same technician, THEN the soft-deleted appointment does not cause a conflict.
- **AC4.** GIVEN an appointment with `trang_thai = HOAN_TAT`, WHEN the manager requests DELETE, THEN the system rejects the request with HTTP 422.

## 5. Constraints and Business Rules

| ID | Rule | Type | Enforced at |
|---|---|---|---|
| QT-04 | Due date is generated by priority at ticket creation: `CAO` = 24h, `TRUNG_BINH` = 72h, `THAP` = 120h. L4 consumes `ticket.due_date`; it does not generate it. | Business calculation | L2 / service layer |
| QT-06 | A ticket may only transition status per the lifecycle. Every transition must be logged to `ticket_status_log`. | Lifecycle | Service layer |
| QT-07 | A ticket may be assigned to at most one technician at a time. Changing the technician must be logged with a reason. | Operational | Service layer + log |
| QT-08 | A technician may only be assigned tickets whose issue category they have proficiency ≥ 3 for, and who work at the same service center. | Operational | Service layer |
| QT-13 | No physical deletion of warranty tickets. Only soft delete is allowed. | Data retention | `ticket.is_deleted` |
| QT-14 | Employees may only view data of their own center or store. | Security | Service layer |
| QT-15 | Customer phone numbers are masked for all roles except Center Manager and Board of Directors. | Security | Service layer |
| CON-01 | `appointment.gio_ket_thuc > appointment.gio_bat_dau` | Structural | Database CHECK |
| CON-02 | `appointment.loai IN ('GIAO_MAY', 'NHAN_MAY', 'KIEM_TRA_TAI_CHO')` | Structural | Database CHECK |
| CON-03 | `appointment.trang_thai IN ('DA_DAT', 'DA_XAC_NHAN', 'HOAN_TAT', 'KHACH_HUY', 'KHACH_KHONG_DEN')` | Structural | Database CHECK |
| CON-04 | `technician_skill.proficiency BETWEEN 1 AND 5` | Structural | Database CHECK |
| CON-05 | `ticket.status`, `ticket.priority`, and `ticket.is_warranty` are NOT NULL and use allowed technical values. | Structural | Database NOT NULL / CHECK |
| CON-06 | `appointment.is_deleted` is a boolean flag used for soft delete. Default value is `FALSE`. | Structural | Database default + service layer |

### Design notes

1. **Appointment conflict is blocking in v0.2.** Conflict detection is enforced at the service layer. If an active overlap exists, the system blocks saving until the manager changes the time or cancels the operation. No override is allowed in v0.2.
2. **External master data boundary.** Customer, device/product, service center, and employee master data are external to the L4 prototype. The L4 ticket stores snapshot fields needed for assignment and appointment display: `customer_name`, `customer_phone`, and `serial_no`. `center_id` is used for center scoping. `ticket_status_log.changed_by` stores the acting user identity without a foreign key to an employee table.
3. **Appointment snapshots.** The `appointment` table stores `technician_id` and `center_id` as scheduling-time snapshots. This is justified because reassignment can occur after scheduling, and the appointment event must preserve the technician and center responsible at the time of scheduling.
4. **No appointment location or note in v0.2.** Handover and receipt appointments are associated with the ticket's service center. On-site address handling and appointment notes are deferred.
5. **`ticket.category_id` is NOT NULL.** L2 classifies the issue category before L4 consumes the ticket; eligibility (QT-08) cannot be evaluated without it. Unclassified tickets never enter the L4 queue.
6. **Appointment soft delete.** `appointment.is_deleted` marks an appointment as deleted while preserving the row. Default appointment reads and FR7 conflict checks filter `is_deleted = FALSE`. Completed appointments (`trang_thai = HOAN_TAT`) cannot be soft-deleted in the BT2 prototype.
7. **Technician skill delete.** Deleting a `technician_skill` row removes the technician’s eligibility for that issue category. This table is configuration/support data for QT-08 and is not covered by QT-13 hard-delete protection.
